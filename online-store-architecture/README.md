# Архитектура интернет-магазина с МойСклад

Учебное задание на проектирование интернет-магазина, который ведёт торговлю через собственный контур, а торговый и складской учёт выполняет во внешней системе [МойСклад JSON API 1.2 (Remap)](https://dev.moysklad.ru/doc/api/remap/1.2/).

На этом этапе реализовывать магазин, frontend, backend и платёжную заглушку не нужно. Заглушка Remap API уже есть в [`../remap-stub/README.md`](../remap-stub/README.md): её используют, а не проектируют. Результат работы — архитектурная документация, по которой другую команду можно допустить к реализации без устных пояснений автора.

## С чего начать

1. Прочитайте [TASK.md](TASK.md) целиком. Это единственный документ с постановкой задачи.
2. Откройте [REFERENCES.md](REFERENCES.md) и сверьте факты Remap API с официальной документацией на дату своей работы. Лимиты имеют расписание изменений.
3. Заполняйте файлы в `docs/`, `api/` и `docs/adr/` по шаблонам из `templates/`. Пустые разделы с пометкой `TODO` — ваша работа, а не черновик преподавателя.
4. Критерии оценки — [EVALUATION.md](EVALUATION.md). Вопросы защиты — [DEFENSE.md](DEFENSE.md). Ответы к вопросам не публикуются: на защите нужно обосновывать собственные решения.

## Порядок выполнения

Этапы, артефакты и критерии завершения перечислены в разделе 21 файла [TASK.md](TASK.md). Кратко:

1. Предметная область МойСклад.
2. Бизнес-процессы.
3. Функциональные требования.
4. Нефункциональные требования.
5. Архитектура (C4) и сравнение модульного монолита с микросервисами.
6. Интеграция с Remap API, включая режимы `mock` и `real`. Заглушка режима `mock` уже предоставлена.
7. Модель данных.
8. Публичное API магазина.
9. Согласованность, конкурентный доступ, восстановление.
10. Стратегия тестирования.
11. ADR.
12. Защита.

Документы должны согласовываться между собой. Статус в диаграмме состояний, которого нет в модели данных и в API, считается противоречием.

## Ограничения задания

- Используйте только публичный Remap API 1.2. Внутренние API МойСклад, недоступные внешней интеграции, не рассматриваются.
- Если нужной операции в API нет, зафиксируйте ограничение и предложите архитектурный обход. Не придумывайте эндпоинт.
- Каталог на витрине читается из локальной базы. Открытие страницы каталога не обращается к МойСклад.
- Бизнес-логика магазина не различает реальный API и заглушку. Переключение — конфигурацией `base-url`.
- Режим `mock` ходит в процесс `remap-stub` по HTTP. Набор Mockito-моков внутри магазина это требование не закрывает. Свою заглушку Remap писать не нужно.
- Контракт платёжной заглушки описывается в документации магазина. Это не документ `paymentin`.
- Токен МойСклад не попадает во frontend и в Git.
- Реальные интеграционные тесты выполняются только на выделенном тестовом аккаунте.

## Рекомендуемый стек будущей реализации

Java 21 или новее, Spring Boot, PostgreSQL, Maven, Flyway или Liquibase, Docker, Docker Compose, OpenAPI, JUnit 5, Testcontainers, PlantUML или Mermaid.

Redis, Kafka, RabbitMQ, Prometheus, Grafana, OpenTelemetry, WireMock и MockServer допустимы только вместе с ADR, где объяснено, какую проблему компонент закрывает и почему более простой вариант недостаточен. На этапе проектирования код этих компонентов не пишется.

## Как сдавать

Сдаётся заполненный каталог `online-store-architecture/`:

- нет незакрытых `TODO` в файлах, которые входят в сдачу;
- у каждого функционального требования есть идентификатор и критерии Given / When / Then;
- OpenAPI 3.1 разбирается стандартным валидатором без ошибок синтаксиса;
- каждая диаграмма имеет исходник (`.puml` или `.mmd`) и читается без устного комментария;
- матрица совместимости уже заполнена и ссылается на раздел поведения заглушки; публичное API магазина ссылается на свои FR;
- ADR содержат отклонённые варианты, а не только выбранный.

Защита проходит по вопросам из [DEFENSE.md](DEFENSE.md). Преподаватель может изменить числа в сценарии (другая задержка, другой статус документа, повтор того же `requestId`) и ожидает, что ответ следует из вашей документации.
