# Учебное задание. Архитектура интернет-магазина, интегрированного с МойСклад

Роль студента: системный аналитик и архитектор. Роль преподавателя: заказчик учёта и рецензент архитектуры.

Результат этапа — комплект документов в этом каталоге. Реализация интернет-магазина, платёжной заглушки и заглушки Remap API в объём этапа не входит.

Факты о Remap API ниже сверены с репозиторием [moysklad/api-remap-1.2-doc](https://github.com/moysklad/api-remap-1.2-doc), ветка `pre_release`, на 26 ноября 2026 года. Опубликованная документация может измениться. Перед защитой студент повторно открывает официальные разделы и помечает в `REFERENCES.md` дату своей сверки. Расхождение с этим заданием разрешается в пользу официальной документации на дату сверки; расхождение фиксируется в `docs/integration/moysklad-api.md`.

## 1. Цель

Нужно научиться:

- разбирать бизнес-требования торгового контура;
- читать предметную область складского учёта по первичным документам, а не по названиям таблиц;
- проводить границы между интернет-магазином и внешней учётной системой;
- проектировать интеграцию, модель данных и публичный API;
- удерживать согласованность там, где одна локальная транзакция PostgreSQL не охватывает обе системы;
- записывать решения так, чтобы по ним можно было реализовать систему.

Готовая архитектура в этом репозитории намеренно не выдана. Файлы `docs/` задают состав результата и критерии полноты раздела. Выбор стиля архитектуры, источников истины, момента резервирования, способа синхронизации и набора таблиц остаётся за студентом и защищается в ADR.

## 2. Границы работы

В сдачу входит заполненная документация по структуре раздела 20.

В сдачу не входит:

- код магазина, frontend и заглушек;
- заполненные «от преподавателя» ADR, диаграммы, физическая модель и OpenAPI;
- интеграция с внутренними API МойСклад;
- копирование Remap API в публичное API магазина.

Исходный сценарий оформления заказа в разделе 7.3 — описание бизнеса, которое можно перестроить. Порядок шагов, синхронность и границы транзакций студент определяет сам и показывает, какие отказы этот порядок закрывает.

## 3. Проектируемая система

Интернет-магазин использует МойСклад как внешнюю систему торгового и складского учёта и хранит собственные данные.

Магазин обеспечивает:

- регистрацию и авторизацию покупателей;
- каталог, карточку товара, поиск и фильтрацию;
- категории;
- модификации товара;
- цены;
- доступное количество;
- корзину;
- оформление заказа;
- резервирование;
- оплату через заглушку платёжной системы;
- историю и статус заказа для покупателя;
- отмену заказа;
- отгрузку;
- возврат;
- административное управление заказами.

Страница каталога обслуживается из локальной базы. Вызов Remap API на каждый просмотр категории, карточки или поисковой выдачи запрещён постановкой.

Студент явно назначает источник истины каждому типу данных из раздела 14. Локальная копия, направление синхронизации и правило конфликта входят в матрицу владения.

Участники:

- покупатель;
- администратор магазина (сотрудник, который ведёт заказы в контуре магазина);
- сотрудник, который может изменить документ непосредственно в интерфейсе МойСклад;
- МойСклад;
- заглушка Remap API;
- заглушка платёжной системы.

Платёжная заглушка подтверждает или отклоняет оплату и не является документом `paymentin`. Факт оплаты в учёте и факт оплаты в платёжном контуре — разные записи. Их связь проектируется отдельно.

### 3.1. Нагрузка, от которой считается архитектура

| Параметр | Значение |
|---|---|
| Товары и модификации | 100 000 |
| Покупатели | 10 000 в сутки |
| Заказы | 1 000 в сутки |
| Одновременные пользователи витрины | 200 |
| Склады | 5 |

Эти числа — вход для расчёта, а не готовый профиль нагрузки. Студент сам оценивает:

- чтение каталога и карточек при 200 одновременных сессиях;
- частоту синхронизации каталога, цен, изображений и остатков;
- число запросов Remap API на один заказ, на одну отмену, на один возврат, на одну сверку;
- пиковую нагрузку на API при массовом обновлении остатков и при восстановлении после простоя;
- запас до лимитов раздела 4 с указанием даты, на которую лимит взят.

Расчёт помещается в `docs/requirements/non-functional-requirements.md` и используется в ADR по синхронизации. Утверждение «нагрузки мало, лимиты не важны» без арифметики не принимается.

## 4. Предметная область, которую нужно изучить

Документ `docs/business/glossary.md` и `docs/business/domain-model.md` студент пишет своими словами и ссылается на раздел документации. Ниже — состав изучения и ограничения API. Это не статья-глоссарий, которую можно сдать вместо собственного разбора.

### 4.1. Сущности Remap API 1.2

Имена ниже — ключевые слова JSON API (`meta.type` и сегмент URL).

| Сущность в учёте | Ключевое слово | Зачем она в задании |
|---|---|---|
| Товар | `product` | Карточка номенклатуры, цены, архив, изображения, группа |
| Модификация | `variant` | Отдельная продаваемая позиция со своими характеристиками, ценами, штрихкодами и остатком |
| Группа товаров | `productfolder` | Дерево категорий учёта |
| Ассортимент | `assortment` | Сводная выборка номенклатуры |
| Склад | `store` | Место хранения остатка |
| Организация | `organization` | Юрлицо документа |
| Контрагент | `counterparty` | Покупатель в учёте |
| Заказ покупателя | `customerorder` | Намерение купить, резерв, связь с оплатами и отгрузками |
| Отгрузка | `demand` | Документ, который списывает товар со склада |
| Возврат покупателя | `salesreturn` | Документ, который возвращает товар на склад |
| Входящий платёж | `paymentin` | Поступление денег, связанное с операциями |
| Статус документа | `state` | Пользовательский статус внутри метаданных типа документа |
| Канал продаж | `saleschannel` | Признак канала; для интернет-магазина в перечислении есть значение `ECOMMERCE` |
| Тип цены | `pricetype` | Какая из цен продажи показывается на витрине |
| Отчёт по остаткам | `report/stock` | Остаток, резерв, ожидание, доступное количество, себестоимость |

Ресурсы, которые понадобятся при разборе сценариев и могут войти в минимальный контракт заглушки, если студент докажет их необходимость:

- исходящий платёж `paymentout` — денежный возврат в учёте, отдельный документ от `paymentin`;
- шаблон документа `PUT /entity/{type}/new` — предзаполнение, а не сохранение;
- позиции документа `.../positions`;
- изображения `images`;
- вебхуки `webhook` и вебхук остатков `webhookstock`;
- аудит `audit` — способ обнаружить изменения, уведомление о которых не было доставлено;
- контекст сотрудника `context/employee` и типы цен `context/companysettings/pricetype`;
- метаданные документа, включая коллекцию `states`.

Услуги (`service`), комплекты (`bundle`), партии (`consignment`) и розничные документы (`retaildemand`, `retailshift`) в минимальный объём магазина не входят. Если студент расширяет объём, он описывает влияние на остатки и на контракт заглушки. Молчаливое игнорирование комплекта, который встретится в `assortment`, недопустимо: нужно правило, что с ним делает витрина.

### 4.2. Различия, которые нужно объяснить своими словами

В глоссарии и в доменной модели должны быть разобраны пары:

- товар и модификация;
- артикул и штрихкод;
- остаток, резерв, ожидание и доступное количество;
- заказ покупателя и отгрузка;
- оплата и отгрузка;
- отмена заказа и возврат товара;
- физическое наличие и возможность продажи;
- организация и склад;
- цена продажи и себестоимость.

К каждой паре: определение, какой документ или отчёт это меняет, где лежит источник истины, какая ошибка возникнет, если пара смешана в одной колонке локальной базы.

### 4.3. Факты API, которые нельзя подменять догадкой

#### Номенклатура

- У `product` и `variant` разные `id`. Модификация ссылается на товар полем `product`. В заказе позиция ссылается на ассортимент (`assortment`): это может быть товар или модификация. Продажа товара, у которого есть модификации, и продажа конкретной модификации — разные решения; его нужно принять явно.
- `variant.characteristics` обязательны при создании модификации. `variant.name` приходит в ответе как наименование товара вместе с модификацией.
- `article` — строка артикула длиной до 255. Документация не объявляет артикул уникальным ключом. `code` — отдельное поле кода сущности. Опираться на уникальность артикула можно только после проверки фактических ограничений аккаунта и фиксации этого правила.
- `barcodes` — массив объектов. Формат задаётся именем поля: `ean13`, `ean8`, `code128`, `gtin`, `upc`. Обновление передаёт полный список; отсутствующие элементы удаляются. В фильтре поле указывается в единственном числе: `barcode`.
- У модификации собственные `article`, `barcodes`, `salePrices`, `images`. Наследовать их с товара «по умолчанию в API» нельзя: в ответе модификации приходят её поля.
- `salePrices[]` содержит `value` (число в минимальных единицах валюты, для рубля — копейки), `currency` и `priceType`. Одной скалярной «цены товара» в API нет. `buyPrice` — закупочная цена, тоже объект с `value` и `currency`. Себестоимость в расширенном отчёте остатков — поле `price` в копейках. Это три разных величины.
- `archived=true` оставляет сущность в учёте и убирает её из обычной работы. Одновременный фильтр по `id` и `archived` игнорирует условие архивности. Для витрины нужно отдельное правило: что считать снятым с продажи.
- Изображений не больше 10. В выдаче это метаданные (`filename`, `size`, `miniature`, `tiny`, `title`, `updated`). Скачивание идёт через `downloadHref`: временный URL, редирект, по умолчанию живёт одну минуту. Заголовок `X-Lognex-Download-Expiration-Seconds` поднимает срок до 86400 секунд. Долгоживущие ссылки предназначены для экспорта; выкладывать их на публичную витрину документация запрещает. Миниатюра может быть `null`, пока её не создали обращением по `href`.
- Группа товаров — дерево через `productFolder`. `pathName` только для чтения и меняется вместе с группой.
- `assortment` собирает номенклатуру разных типов. Заголовок `X-Lognex-Remap-Beta-Feature` включает нестабильный контракт. Гарантии неизменности полей на бета-функции не распространяются. Зависимость витрины от бета-заголовка допустима только как явно изолированное решение с планом отказа.

#### Деньги и количества

- Денежные поля документов и цен — `Float` в минимальных единицах валюты, если в описании поля указаны копейки. Количество — `Float`: весовой товар законен. Локальное хранение денег и количеств студент выбирает сам и описывает правила округления.
- `sum` заказа, отгрузки и возврата только для чтения и вычисляется учётом. `sum` входящего платежа записывается клиентом интеграции.
- Дата-время в API — строка `гггг-мм-дд чч:мм:сс`, например `2016-08-23 15:21:09`. Это не ISO-8601 с `T` и `Z`. Часовой пояс студент устанавливает по документации аккаунта и не подменяет его догадкой UTC.

#### Складской учёт

Расширенный отчёт `GET /report/stock/all` и `GET /report/stock/bystore` возвращает, среди прочего:

| Поле отчёта | Смысл в документации |
|---|---|
| `stock` | Остаток |
| `reserve` | Резерв |
| `inTransit` | Ожидание |
| `quantity` | Доступно |
| `price` | Себестоимость в копейках |
| `salePrice` | Цена продажи |

Краткий отчёт `GET /report/stock/all/current` и `GET /report/stock/bystore/current` возвращает один вид величины за запрос, параметр `stockType`:

| `stockType` | Смысл в документации |
|---|---|
| `stock` | Физический остаток без учёта резерва и ожидания. Значение по умолчанию |
| `freeStock` | Остаток за вычетом резерва |
| `quantity` | Доступно. Учитывает резерв и ожидания |
| `reserve` | Резерв |
| `inTransit` | Ожидание |

`quantity` и `freeStock` — разные показатели. Продажа по `quantity` может учитывать товар, которого физически ещё нет (`inTransit`). Можно ли продавать ожидание, студент решает отдельно от выбора эндпоинта и записывает это бизнес-правилом.

Дополнительные факты краткого отчёта:

- ответ приходит одним массивом, без постраничного `limit`/`offset`, порядок строк не задан;
- по умолчанию нулевые строки скрыты; `include=zeroLines` их показывает;
- товар, который создан и не участвовал в операциях, в отчёт не попадает;
- `changedSince` отбирает номенклатуру, у которой показатель менялся в интервале, и возвращает фактическое значение на момент запроса, а не дельту и не остаток «на тот момент»;
- `changedSince` не дальше 24 часов в прошлое и не в будущем; при его использовании нулевые строки включены;
- удалённый или архивированный за интервал товар приходит с нулём, а последующий GET по id может завершиться отсутствием сущности;
- документация рекомендует перекрытие соседних интервалов и полную синхронизацию без `changedSince` не реже раза в сутки;
- остатки в отчёте — уже пересчитанные на момент запроса. Пересчёт в МойСклад не мгновенный. Для `GET /report/stock/bystore/current` параметр `withRecalculate=true` добавляет ещё не пересчитанные строки со значением `null`;
- строка без склада в разрезе по складам содержит резервы, не привязанные к складу;
- краткий отчёт доступен администратору или сотруднику с правом на остатки. Себестоимость в расширенном отчёте зависит от прав видимости.

В позициях документа параметр `fields=stock` возвращает другой объект: в примере документации у позиции есть `quantity`, `reserve`, `intransit`, `available`, `cost`. Имена не совпадают с полями отчёта. Переносить смысл поля `quantity` из отчёта в позицию документа нельзя. В одном запросе допускается одно значение `fields`; `fields=stock,declaration` — ошибка 3042. Вместе с `expand` выборка не больше 100 элементов, иначе `fields` и `expand` игнорируются. Для заказа остаток в `fields=stock` считается на текущий момент, для отгрузки и возврата — на `moment` документа.

Резерв позиции заказа — поле `reserve`. Ошибка 17003: количество в резерве не может превышать количество позиции. Поле `shipped` позиции заказа только для чтения. `reservedSum`, `shippedSum`, `payedSum` заказа только для чтения.

Отдельного ресурса «резерв» нет. Резерв задаётся полем позиции заказа. Отдельного ресурса «отмена заказа» нет. Проведение — булево поле `applicable` («отметка о проведении»). Статус `state` сам по себе не списывает и не резервирует товар: это ссылка на пользовательский статус.

Как именно проведённый заказ, отгрузка, снятие проведения и возврат меняют `stock`, `reserve`, `shipped` и `payedSum`, студент подтверждает статьями поддержки и, при доступе к тестовому аккаунту, экспериментом. В документации архитектуры это правило должно быть записано как проверенное, со ссылкой на источник, а не как пересказ данного задания.

Отгрузка связывается с заказом полем `customerOrder`. Проведённая отгрузка требует склад. `PUT /entity/demand/new` с телом, где указан заказ, возвращает предзаполненный шаблон и не создаёт документ. Создание — отдельный `POST /entity/demand`. Частичная отгрузка выражается количеством в позициях отгрузки, меньшим, чем количество в заказе. Отдельного флага «частичная отгрузка» нет.

Возврат с основанием ссылается на отгрузку полем `demand`. Возврат без основания документация различает: у такой позиции себестоимость ведёт себя иначе. Частичный возврат — количество в позиции возврата. Отдельного ресурса «вернуть одну штуку из трёх» нет. `payedSum` возврата — сумма исходящих платежей.

Входящий платёж не является складским документом. Связь с заказом, отгрузкой и другими разрешёнными операциями задаётся коллекцией `operations` с `linkedSum`. Разрешённые типы включают `customerorder` и `demand`. Если заполнен валютный счёт организации, валюта платежа должна с ним совпадать, иначе ошибка 22004. Приходный ордер `cashin` — другой документ, не замена `paymentin`.

Организация и склад независимы: в документе нужны оба, остаток живёт на складе. Канал продаж можно указать в заказе, отгрузке и возврате. Тип канала `ECOMMERCE` не создаёт технической изоляции остатка: другой канал того же склада продаёт тот же `stock`.

#### Статусы

Статусы читаются из метаданных типа документа, например `GET /entity/customerorder/metadata`, коллекция `states`. Поля статуса: `name`, `color`, `stateType`. Тип статуса: `Regular`, `Successful`, `Unsuccessful`. Набор имён не фиксирован API. Создавать статусы может администратор. Магазин не имеет права считать строку `RESERVED` существующей, пока она не заведена в аккаунте и не сопоставлена с локальным состоянием.

Удаление документа: `DELETE` может вернуть 409, если есть зависимости (`dependencies` в ошибке). Удаление в корзину — `POST /entity/{type}/{id}/trash`. Восстановление из корзины через API отсутствует, только через UI. Поле `deleted` — момент последнего удаления, только для чтения.

Обновление заказа с массивом `positions` заменяет всю коллекцию позиций: лишние удаляются, новые добавляются. То же правило действует для отгрузки и возврата. В одном массиве не больше 1000 элементов, иначе 413. Дальше позиции дополняются ресурсом `.../positions`.

#### Идентичность и повтор создания

Заголовка `Idempotency-Key` у Remap API нет.

Поле `syncId` как раз предназначено для повтора создания: клиент передаёт свой UUID при создании; повтор того же запроса с тем же `syncId` возвращает уже созданную сущность, а не вторую копию. После заполнения `syncId` не меняется. Удаление такой сущности возможно по URL вида `/entity/{type}/syncid/{id}`. У товара в таблице атрибутов `syncId` помечен как заполняемый при создании и только для чтения в последующих ответах; у заказа, отгрузки, возврата и платежа поле фильтруется и тоже не меняется после заполнения. Студент проверяет, у каких сущностей минимального контракта `syncId` действительно есть, и не распространяет правило на сущности без этого поля.

`externalCode` — внешний код до 255 символов. Сам по себе он не описан как механизм дедупликации создания. Использовать его как ключ сверки можно только вместе с правилом уникальности, которое студент проверил.

`id` сущности — UUID, назначаемый МойСклад.

#### Ошибки и протокол

Тело ошибки: `{ "errors": [ { "error", "code", "error_message", "moreInfo", "parameter", "line", "column", "dependencies", "meta" } ] }`. Код внутри тела может отсутствовать; тогда смысл даёт HTTP-статус.

Обязателен заголовок `Accept-Encoding: gzip`. Иная ситуация завершается 415 без тела. В ответе возможны и несжатые тела; признак сжатия — `Content-Encoding`.

Нужно уметь обработать как минимум: 400, 401, 403, 404, 409, 412, 413, 414, 415, 429, 500, 502, 503, 504. Для 301/303/308 учитывать `Location`. Скачивание файла требует поддержки редиректа; временный URL файла авторизации не требует.

Коды, которые уже нужны сценариям задания:

| Код | Смысл |
|---|---|
| 1049 | Превышен лимит запросов в единицу времени |
| 1073 | Превышен лимит одновременных запросов. Заголовки остатка лимита этот предел не показывают |
| 17003 | Резерв позиции больше количества позиции |
| 22004 | Валюта платежа не совпадает с валютой счёта организации |
| 3042 | В `fields` передано больше одного значения |

Полный перечень студент не копирует в документацию. Он включает те коды, на которые опирается обработка ошибок его сценариев, и даёт ссылку на справочник ошибок.

#### Лимиты

С 16 февраля 2026 года бюджет запросов считается отдельно на пользователя и отдельно на решение, а не одной корзиной на аккаунт. Каждые 3 секунды выдаётся 45 единиц. Вес обычного запроса зависит от способа входа:

| Способ входа | Вес обычного запроса | Запросов за 3 секунды |
|---|---|---|
| Токен опубликованного публичного или приватного решения | 1 | 45 |
| Логин/пароль или токен пользователя с 12 мая 2026 | 2 | 22 |
| Логин/пароль или токен пользователя с 1 сентября 2026 | 3 | 15 |
| Логин/пароль или токен пользователя с 1 декабря 2026 | 4 | 11 |
| Токен решения в статусе «Черновик» или «На модерации» с 13 апреля 2026 | 4 | 11 |

`GET /report/stock/all` и `GET /report/stock/bystore` стоят 5 единиц независимо от способа входа. Краткий отчёт `/current` в списке повышенного веса не указан.

Не зависят от способа входа:

- не больше 5 параллельных запросов от пользователя или решения;
- не больше 20 параллельных запросов от аккаунта;
- не больше 8 КБ заголовков;
- не больше 20 МБ тела;
- не больше 4 асинхронных задач в очереди на аккаунт;
- не больше 1000 элементов в одном массиве.

Заголовки остатка: `X-RateLimit-Limit`, `X-Lognex-Retry-TimeInterval`, `X-RateLimit-Remaining`, `X-Lognex-Reset`, `X-Lognex-Retry-After`. При 429 запрос повторяют после времени сброса, а не немедленно.

Автоматическое отключение доступа к API, если в течение последнего часа пользователь:

- больше 200 идентичных ошибочных запросов в минуту;
- больше 200 ответов 429 в минуту;
- больше 100 PUT одной и той же сущности в минуту.

Восстановление доступа к API — через поддержку МойСклад. Вебхуки при длительной ошибке приёмника отключаются отдельно (раздел про вебхуки) и включаются самим клиентом.

Новый токен пользователя, полученный `POST /security/token`, отзывает ранее выданные токены этого пользователя. Две интеграции на одном сотруднике этот вызов ломает. Для учебного стенда заводится отдельный сотрудник тестового аккаунта.

Пагинация списков: `limit` от 1 до 1000, по умолчанию 1000, `offset`, в `meta` приходят `size`, `limit`, `offset`, при переполнении страницы — `nextHref` и `previousHref`. `expand` разрешён на выборке не больше 100 и на глубине не больше 3; при большем `limit` параметр молча игнорируется.

Массовые `POST` массива и `POST /entity/{type}/delete` ограничены 1000 объектами. Обработка длиннее 5 минут обрывается по таймауту; размер пачки тогда уменьшают.

Тариф ограничивает функции. Вебхуки создаются и доставляются на платном тарифе и в пробный период. На бесплатном тарифе вебхук не создать и уведомления не отправляются. В допущениях архитектуры указывается тариф, на который она рассчитана.

#### Вебхуки

`POST /entity/webhook`. Уведомление — `POST` на URL подписчика с query-параметром `requestId`. Тело содержит `auditContext` и массив `events`. Событие содержит `meta` изменённой сущности, `action` (`CREATE`, `UPDATE`, `DELETE`, для асинхронных задач ещё `PROCESSED`), `accountId` и, если вебхук создан с `action=UPDATE` и `diffType=FIELDS`, массив `updatedFields`. Полного документа в теле нет. Актуальные данные читаются по `meta.href`. Для `DELETE` сущность к моменту чтения уже может отсутствовать.

Ответ подписчика: HTTP 200 или 204 не позднее 1500 мс. Иначе выполняются ещё 3 попытки подряд, без паузы. Если все попытки неуспешны, уведомление считается неотправленным и удаляется. Повторной выдачи этого уведомления позже API не обещает. Повтор в рамках этих попыток узнаётся по тому же `requestId`. Приём и обработку разделяют, чтобы уложиться в 1500 мс.

Сочетание `entityType` + `action` + `url` уникально. На одну пару `entityType` + `action` — не больше 5 URL у пользователя и не больше 1 у решения. Вебхуки API 1.2 не управляют вебхуками, созданными другими версиями. Управление доступно администратору аккаунта и решению со специальными правами.

Заголовок отключения вебхуков на один исходящий запрос интеграции — `X-Lognex-WebHook-DisableByPrefix`. Префикс включает схему и полное доменное имя. Несколько префиксов передаются несколькими заголовками, не списком через запятую. Короткий префикс вроде `https://` отклоняется.

Если больше семи дней из последних десяти приёмник отвечал только ошибками или был недоступен и ни одного успешного приёма за десять дней не было, вебхуки отключаются. Письмо уходит владельцу аккаунта. Включение выполняется клиентом, поддержка для этого не требуется.

`webhookstock` — отдельная сущность. Уведомление уходит раз в 1–5 минут, если остатки менялись. Тело содержит `accountId`, `stockType` (на данный момент значение `stock`), `reportType` (`all` или `bystore`) и `reportUrl` на краткий отчёт с `changedSince`. Позиций и дельты в теле нет. Правила ответа 200/204, 1500 мс и трёх повторов те же, ключ повтора — `requestId`.

Порядок разных уведомлений относительно друг друга документация не гарантирует. Одно уведомление может содержать несколько `events`.

Аудит (`GET /audit` и ссылка из `auditContext.meta`) нужен как канал восстановления пропущенных изменений. Отдельного API «повторите недоставленные вебхуки» в изученной документации нет. Если студент такой ресурс найдёт в более новой документации, он ссылается на раздел и пересматривает решение.

### 4.4. Чего в API нет

Эти отсутствующие возможности нужно явно закрыть архитектурой магазина, а не вызовом несуществующего метода:

- регистрация и сессия покупателя витрины;
- корзина;
- единый конечный автомат заказа с состояниями вроде `PAID` и `SHIPPED` (в учёте это набор документов и пользовательских статусов);
- атомарная операция «проверить остаток и создать заказ» между витриной и МойСклад;
- блокировка остатка на время HTTP-запроса витрины;
- заголовок идемпотентности, общий для всех ресурсов;
- гарантия, что вебхук будет доставлен после исчерпания четырёх попыток;
- мгновенная согласованность отчёта остатков с только что проведённым документом;
- изоляция остатка интернет-магазина от других каналов на том же складе;
- возврат денег платёжным шлюзом силами `paymentin`;
- восстановление документа из корзины через API;
- публичная постоянная ссылка на изображение, пригодная для витрины без ограничений документации.

## 5. Режимы интеграции

Предусматриваются два режима. Бизнес-логика магазина от режима не зависит.

```yaml
moysklad:
  mode: mock
  base-url: http://moysklad-stub:8080/api/remap/1.2
  token: ${MOYSKLAD_TOKEN:}
```

```yaml
moysklad:
  mode: real
  base-url: https://api.moysklad.ru/api/remap/1.2
  token: ${MOYSKLAD_TOKEN}
```

Имена ключей можно уточнить, смысл сохраняется: режим, базовый URL и токен приходят из конфигурации и секретного хранилища. В `real` токен обязателен. В репозитории лежит пример без значения секрета.

Интеграционный слой выделяется явно. Студент сравнивает и выбирает один основной подход, остальные может использовать локально, если объяснит границу:

- Adapter;
- Ports and Adapters;
- Anti-Corruption Layer;
- Gateway.

В сравнении должно быть видно, где живёт преобразование моделей магазина в `meta`, копейки, `applicable`, `reserve`, `operations` и обратно. Доменный сервис магазина не собирает JSON Remap и не ветвится по `mode`.

Заглушка платёжной системы тоже скрыта портом. Её контракт описывается в публичной документации магазина как внешняя зависимость, без притворства, что это Remap API.

## 6. Заглушка Remap API

Заглушка — отдельный HTTP-сервис, stateful между запросами. Она совместима с тем подмножеством Remap API 1.2, которое нужно сценариям задания. Весь API реализовывать не требуется. Минимальный набор студент выводит из процессов и заносит в `docs/integration/api-compatibility-matrix.md`.

Заглушка воспроизводит для выбранного подмножества:

- методы, пути, коды и тела, как в документации;
- объекты `meta` и ссылки между сущностями;
- UUID;
- пагинацию, фильтры и сортировку, которые реально использует магазин;
- структуру `errors`;
- проверку авторизации, достаточную, чтобы магазин не отличал режим по форме ответа;
- создание, чтение, изменение, удаление нужных сущностей;
- влияние проведённых документов на остаток, резерв и ожидание согласно правилам, которые студент зафиксировал и может объяснить;
- частичную отгрузку и возврат части количества;
- вебхуки выбранных событий, включая повтор с тем же `requestId`.

Управляющие операции заглушки лежат вне дерева `/api/remap/1.2`. Через них сценарий теста может:

- сбросить состояние;
- загрузить набор данных;
- задать искусственную задержку;
- вернуть 429, 500, 503;
- оборвать соединение и не ответить до таймаута клиента;
- повторить вебхук;
- доставить события в нарушенном порядке;
- включить окно недоступности;
- сохранить документ и не вернуть HTTP-ответ клиенту.

Контракт этих управляющих операций описывается в `api/moysklad-stub-openapi.yaml` и не смешивается с имитацией Remap.

Нужен способ контрактной проверки заглушки против реального API на тестовом аккаунте: какие запросы гоняются в обе стороны, как сравниваются тела, какие поля заранее исключены (сгенерированные `id`, `moment`, временные `downloadHref`). WireMock и MockServer можно обсудить в ADR как инструмент контрактного теста. Они не заменяют stateful-заглушку сценариев, если не исполняют правила остатков и повторную доставку.

## 7. Бизнес-процессы

Описание процессов — `docs/business/business-processes.md` плюс диаграммы из раздела 12.2. Для каждого процесса: участники, границы систем, развилки, параллельные ветки, таймеры, ошибки, повторы, компенсации, данные на входе и выходе, источник истины.

### 7.1. Синхронизация каталога

Разобрать:

- первичную загрузку;
- группы товаров;
- товары и модификации;
- цены выбранного `pricetype`;
- изображения с учётом срока `downloadHref` и запрета публиковать долгоживущие ссылки;
- обновление уже загруженных карточек;
- архивирование и возврат из архива;
- периодичность;
- ошибку отдельной страницы и ошибку всего прогона;
- простой МойСклад дольше одного цикла, включая простой в несколько часов.

Сравнить вебхуки сущностей, опрос по `updated` и смешанную схему. Указать, как обнаруживается пропущенное уведомление (аудит, полная сверка, фильтр по времени) и как исключается вечная потеря архивированного товара.

Полный обход 100 000 карточек через `limit=1000` студент пересчитывает в запросах, во времени и в единицах лимита. `expand` на таком обходе недоступен: при `limit` больше 100 он игнорируется.

### 7.2. Синхронизация остатков

Разобрать:

- остатки по пяти складам и правило, какой склад продаёт витрина;
- показатель, который витрина называет доступным количеством (`stock`, `freeStock` или `quantity`), и почему;
- обновление локальной проекции;
- резерв, созданный магазином и созданный другим каналом;
- изменение остатка руками в МойСклад (приёмка, списание, инвентаризация, чужая отгрузка — достаточно показать, что витрина видит следствие в отчёте, не реализуя эти документы);
- устаревшую проекцию и пересчёт, который ещё не закончился (`null` при `withRecalculate`);
- запрет продать отсутствующее сверх принятого бизнес-правила.

Студент назначает допустимую задержку и связывает её с выбором краткого отчёта, `changedSince`, `webhookstock` и полной суточной сверки. Расширенный отчёт как частый опрос требует отдельного обоснования из-за веса 5 и объёма 100 000 строк.

Локальная проекция остатка не объявляется источником истины, если студент не докажет обратное. Даже при локальном резерве физический остаток принадлежит учёту.

### 7.3. Оформление заказа

Исходный сценарий заказчика, его можно перестроить:

1. Покупатель собирает корзину.
2. Магазин проверяет, можно ли оформить заказ.
3. Проверяются актуальные цены.
4. Проверяется доступное количество.
5. Создаётся локальный заказ.
6. В МойСклад находится или создаётся контрагент.
7. Создаётся заказ покупателя.
8. Резервируется товар.
9. Покупатель платит.
10. Оплата фиксируется в платёжном контуре и в учёте.
11. Заказ передаётся на комплектацию.
12. Создаётся отгрузка.
13. Заказ достигает конечного состояния.

Нужно определить синхронные и асинхронные шаги, границы локальных транзакций, что видит покупатель, пока МойСклад недоступен, и какой шаг повторяем. Создание заказа в МойСклад при уже созданном локальном заказе не должно порождать второй `customerorder` после таймаута: здесь уместно разобрать `syncId` и локальный ключ идемпотентности.

Проверка цены в момент оформления учитывает, что цена в корзине могла устареть. Правило «какую цену платит покупатель» фиксируется до обсуждения блокировок.

### 7.4. Отмена

Отдельные случаи:

- локальный заказ ещё не отправлен в МойСклад;
- `customerorder` создан;
- резерв уже поставлен (`reserve` и `applicable`);
- оплата прошла в платёжной заглушке, `paymentin` ещё не создан;
- `paymentin` создан;
- идёт комплектация, отгрузки ещё нет;
- отгрузка создана частично;
- отмена и отгрузка начинаются одновременно.

Для каждого случая: допустима ли отмена, кто инициатор, что происходит с резервом, с платежом, с документом (`applicable`, статус, `DELETE`, корзина), какая компенсация запускается при сбое на полпути. Удаление в корзину без возможности восстановить документ через API — сознательное решение, если студент его выбирает.

### 7.5. Возврат

Предусмотреть полный возврат, возврат отдельных позиций, возврат части количества позиции, возврат денег, поведение остатка. Основание возврата — отгрузка, не заказ, если студент следует документу `salesreturn` с полем `demand`. Возврат до отгрузки — это отмена, и смешивать её с `salesreturn` нельзя.

Деньги: заглушка платёжной системы и документ учёта (`paymentout` или иной документ, который студент найдёт в документации и обоснует). Частичный денежный возврат сверяется с `linkedSum` и с суммой позиции, а не списывается «всем платежом».

### 7.6. Изменение заказа в интерфейсе МойСклад

Сотрудник меняет количество, цену, статус, склад, создаёт отгрузку, снимает проведение, удаляет документ. Студент задаёт:

- какие изменения магазин принимает;
- какие считает конфликтом и чьё значение побеждает;
- как покупатель видит расхождение цены и состава;
- что происходит с локальным резервом и оплатой;
- как отличить изменение, сделанное самим магазином, от изменения сотрудника (контекст аудита, `uid`, отдельный сотрудник интеграции).

Запретить сотруднику редактировать документ силами API нельзя: интерфейс МойСклад остаётся доступен. Архитектура строится на обнаружении и правиле конфликта.

## 12. Согласованность и конкурентный доступ

Текст — `docs/integration/consistency.md` и `docs/database/concurrency.md`. Решения выбираются под конкретную проблему. Применять весь список паттернов не требуется. Для каждой проблемы из списка ниже в тексте есть выбранный механизм и хотя бы один отклонённый.

Проблемы:

1. Два покупателя одновременно берут последнюю единицу.
2. Покупатель повторно отправляет оформление.
3. МойСклад создал заказ, HTTP-ответ потерян.
4. Платёж прошёл, локальный заказ не обновился.
5. Резерв в учёте есть, оплата завершилась ошибкой.
6. Отмена и отгрузка исполняются одновременно.
7. Вебхук доставлен несколько раз с одним `requestId`.
8. События пришли в порядке, отличном от порядка изменений.
9. Процесс магазина оборвался перезапуском.
10. Локальные остатки разошлись с отчётом.
11. Тот же склад продаёт товар через другой канал.
12. Цена изменилась, пока покупатель оформлял заказ.

Механизмы, которые нужно понимать и сравнивать применительно к выбранным проблемам:

- оптимистическая блокировка;
- пессимистическая блокировка;
- `SELECT FOR UPDATE`;
- `SELECT FOR NO KEY UPDATE`;
- атомарный `UPDATE` с проверкой количества в условии;
- уникальные ограничения;
- идемпотентность и ключ идемпотентности на стороне магазина;
- `syncId` на стороне Remap;
- повтор и экспоненциальная пауза;
- circuit breaker;
- transactional outbox;
- transactional inbox;
- saga и компенсация;
- итоговая согласованность;
- сверка (reconciliation).

Обязательное объяснение: транзакция PostgreSQL фиксирует только локальные строки. Вызов Remap API происходит в другом процессе с собственными ошибками, таймаутами и частичным успехом. Успешный `COMMIT` не создаёт `customerorder` и не откатывает его. Отсюда вытекает, где проходит граница транзакции и какая запись переживает перезапуск.

Отдельное объяснение: строковая блокировка в базе магазина не видит продажу другого канала и ручную отгрузку в МойСклад. Она уменьшает гонку внутри магазина и не заменяет правило расхождения с отчётом остатков.

Локальный резерв на витрине, если он вводится, имеет срок жизни и сверку с `reserve` заказа в учёте. Бессрочная локальная «бронь» без документа в МойСклад считается решением, которое нужно явно защитить.

## 17. Стратегия тестирования

`docs/testing/test-strategy.md` и `docs/testing/test-scenarios.md`.

Уровни: unit, integration, contract, end-to-end, load, concurrency, fault injection.

Режим `mock`: тесты ходят в заглушку по HTTP, проверяют остатки, повтор вебхука и потерю ответа. Режим `real`: только выделенный тестовый аккаунт, отдельный токен, запрет на учётные данные рабочего аккаунта, очистка или изоляция созданных документов, чтобы повторный прогон не плодил контрагентов. Контрактный тест сверяет заглушку с реальным API на узком наборе запросов.

Сценарии покрывают основные процессы и отказы: 429, 500, 503, таймаут, обрыв после сохранения документа, дубль `requestId`, нарушенный порядок событий, конфликт отмены и отгрузки, частичный возврат, простой дольше окна `changedSince` (24 часа).

На этом этапе тест-код не пишется. Сценарий по шаблону `templates/test-case-template.md` должен быть достаточным, чтобы его перенесли в автотест без новых продуктовых решений.

## 22. Самопроверка перед сдачей

- Термины совпадают с Remap API: `customerorder`, `demand`, `salesreturn`, `paymentin`, `variant`, `productfolder`, `webhookstock`.
- Нет эндпоинта, которого нет в документации, либо рядом стоит пометка «в API отсутствует» и обходное решение.
- Каталог не читается из МойСклад на каждый запрос витрины.
- `quantity`, `freeStock` и `stock` не использованы как синонимы.
- `PUT /entity/demand/new` не назван созданием отгрузки.
- Потеря HTTP-ответа не создаёт второй документ: назван конкретный механизм (`syncId` и локальная запись).
- Вебхук не считается надёжной очередью.
- `changedSince` не описан как дельта количества.
- Локальная блокировка не объявлена защитой от другого канала продаж.
- Транзакция PostgreSQL не объявлена распределённой транзакцией с МойСклад.
- Токен отсутствует в примерах, во frontend и в составе публичного API.
- Матрица совместимости, состояния заказа, модель данных и OpenAPI называют одни и те же сущности.
- Нагрузка 100 000 позиций и лимит запросов посчитаны, а не упомянуты.
