# Безопасность

## Аутентификация

Как покупатель регистрируется и входит. Где хранится пароль (алгоритм и параметры — конкретные, не «надёжное хеширование»). Как завершается сессия.

Администратор входит отдельно. Общая учётная запись магазина и сотрудника МойСклад не используется: токен интеграции принадлежит техническому сотруднику тестового или рабочего аккаунта и в пользовательский пароль не превращается.

## Авторизация

Роли минимум: покупатель и администратор. Таблица операций публичного API и ролей. Покупатель читает и меняет только свои корзину, заказы и возвраты. Администратор ведёт заказы, отгрузки и возвраты в рамках процесса и не получает токен МойСклад через API магазина.

## Секреты

| Секрет | Где хранится | Кто читает | Где отсутствует |
|---|---|---|---|
| Пароль покупателя | | | логи, Git, МойСклад |
| Токен МойСклад | | только backend режима `real` | frontend, Git, логи, публичное API |
| Секрет приёма вебхука, если он есть | | | |

Новый `POST /security/token` отзывает прежние токены пользователя. В документе сказано, какой сотрудник заведён под интеграцию и почему учебный стенд не делит его с другой системой.

## Персональные данные

Какие поля уходят в `counterparty`, какие остаются только в магазине, зачем, как долго хранятся в логах. Примеры в документации обезличены.

## Вебхуки

Опишите фактические средства проверки, которые даёт документация Remap API на дату сверки. Если подписи тела нет, запишите выбранный контроль (сетевой контур, секрет пути, немедленная сверка `meta.href` с API) и оставшийся риск. Ответ 200 до проверки подлинности источника, если вы его допускаете, ограничен записью в inbox и не меняет заказ до сверки.

## Повторы и аудит

Какие административные действия пишутся в журнал: смена статуса, отмена, отгрузка, возврат, ручной запуск сверки. Журнал содержит сотрудника магазина, идентификатор заказа и correlation id, и не содержит токен.

## Логи

Перечень полей, которые маскируются. Ошибка 401 от МойСклад не приводит к печати заголовка `Authorization`.
