# Модель данных

Три уровня. Диаграммы: `docs/diagrams/er/conceptual.puml`, `logical.puml`, `physical.puml`.

Кандидаты таблиц из задания не обязательны все. Каждая включённая таблица отвечает на вопрос «какой сценарий её пишет и читает». Каждая исключённая из числа тех, без которых ваш сценарий не живёт, объясняется здесь же.

Кандидаты: `User`, `Customer`, `Product`, `ProductVariant`, `Category`, `Price`, `Warehouse`, `Stock`, `Cart`, `CartItem`, `Order`, `OrderItem`, `Payment`, `Reservation`, `Shipment`, `Return`, `ExternalEntityMapping`, `SynchronizationState`, `OutboxEvent`, `InboxEvent`.

## Концептуальная модель

Сущности и связи языком предметной области, без типов столбцов. Покажите отдельно контур витрины и соответствие сущности учёта, не сливая покупателя с контрагентом.

## Логическая модель

Атрибуты, обязательность, уникальность, кардинальность. Деньги и количество — с правилом точности. Статус заказа — перечисление, совпадающее с автоматом.

## Физическая модель

Для каждой таблицы:

| Таблица | PK | FK и правило удаления | Уникальность | Обязательные поля | Кто владеет строкой | Связь с Remap API |
|---|---|---|---|---|---|---|
| | | | | | | |

Правило удаления не оставляет заказ без позиций и не удаляет историю заказа каскадом от архивации товара. Товар, снятый с продажи, остаётся читаемым в старом заказе.

`ExternalEntityMapping` или эквивалент хранит тип сущности, внешний UUID, локальный ключ и, если используете, `syncId`. Один локальный заказ сопоставляется не больше чем с одним `customerorder`.

Если исходящая работа хранится в outbox, запись outbox создаётся в той же локальной транзакции, что и изменение заказа. Иначе объясните, как перезапуск не теряет и не дублирует отправку.

Индексы выносятся в [`indexes.md`](indexes.md). Блокировки — в [`concurrency.md`](concurrency.md).
