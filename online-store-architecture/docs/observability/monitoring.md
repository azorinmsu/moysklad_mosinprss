# Наблюдаемость

## Журналы

Структурированные поля: время, уровень, correlation id бизнес-операции, trace id, идентификатор локального заказа, тип и id сущности МойСклад, HTTP-статус внешнего вызова, код ошибки из тела `errors`, `requestId` вебхука. Токен и пароль в эти поля не входят.

Связь идентификаторов: один оформление порождает локальный correlation id; исходящие вызовы его наследуют; входящий вебхук имеет собственный `requestId` и привязывается к заказу, когда сущность распознана.

## Трассировка

Какие границы создают span: HTTP витрины, транзакция базы, вызов Remap, вызов платёжной заглушки, обработка вебхука. Если распределённая трассировка отложена, напишите, каким набором полей лога вы соберёте путь заказа без неё, и в каком ADR это принято.

| Метрика | Зачем | Порог оповещения | Что делает дежурный или учебный прогон |

| HTTP 429 | | | отдельно 1049 и 1073 |

| Несогласованные заказы | | | |

Технические метрики адаптера: число запросов, остаток лимита по заголовку `X-RateLimit-Remaining`, время ответа, доля таймаутов. Заголовок не показывает параллельный лимит: опишите, как замечаете 1073.

Если очереди нет, метрика необработанных сообщений определяется для той таблицы, которая эту очередь заменяет (outbox, inbox).

## Синхронизация

Видно время успешной полной сверки каталога, успешной полной сверки остатков, последнюю ошибку страницы и признак отключения вебхуков, если вы умеете его получить или выводите его из отсутствия событий при живом изменении в учёте.

## Оповещения

Минимальный набор: всплеск 429, синхронизация остатков старше допустимой задержки, рост несогласованных заказов, заказ завис в промежуточном состоянии, приёмник вебхуков отвечает ошибками. Для учебного стенда достаточно правила и текста оповещения, без обязательной боевой интеграции с мессенджером.
