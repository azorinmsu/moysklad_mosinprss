# Функциональные требования

Заполните по шаблону [`../../templates/requirement-template.md`](../../templates/requirement-template.md).

Минимальные области идентификаторов: `CATALOG`, `STOCK`, `CART`, `ORDER`, `PAYMENT`, `SHIPMENT`, `RETURN`, `CANCEL`, `ADMIN`, `SYNC`, `INTEGRATION`, `SECURITY`.

Нумерация с `001` внутри области. Пропущенный номер допустим, повтор — нет.

## Покрытие, которое должно набраться

Требования в сумме описывают поведение из раздела 3 задания. Отдельное требование заводится там, где у сценария другой результат или другой участник, а не на каждый абзац постановки.

Проверьте наличие наблюдаемого поведения для:

- регистрации и входа покупателя, отказа в чужом заказе;
- каталога, карточки, поиска, фильтра, категорий, модификаций;
- цены выбранного типа и количества, которое разрешено показать;
- корзины и повторного добавления той же модификации;
- оформления при достаточном и недостаточном количестве;
- устаревшей цены;
- оплаты успешной, отклонённой и неопределённой (ответ потерян);
- истории заказов и статуса;
- отмены на этапах, которые вы признали допустимыми, и отказа на остальных;
- отгрузки администратором, включая частичную;
- полного и частичного возврата;
- архивного товара;
- расхождения локальных данных с учётом после правки в МойСклад;
- повтора запроса оформления и повтора вебхука.

Интеграционные требования описывают результат для систем («в учёте один заказ», «резерв снят»), а не имя класса.

Критерии Given / When / Then копируются в [`acceptance-criteria.md`](acceptance-criteria.md) только если они сквозные для нескольких FR. Остальные остаются при требовании, чтобы не плодить две правды.
