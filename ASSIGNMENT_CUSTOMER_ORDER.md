# Учебное задание: обработка заказа покупателя (Camunda 7.24 + МойСклад)

**Уровень:** Intern / Junior Java  
**Тема:** автоматизация обработки заказа покупателя в МойСклад — проверка остатков, резервирование, отгрузка, отмена и компенсация.

Это **отдельное** задание от изменения `AggregateStock` / Sales в основном [README.md](README.md). Заглушка Remap API: [REMAP_STUB.md](REMAP_STUB.md).

---

## 1. Цель

Спроектировать и реализовать исполняемый бизнес-процесс на **Camunda 7.24 Embedded** из **восьми основных этапов**, интегрированный с Remap API 1.2 через **java-remap-1.2-sdk** (заглушка в этом репозитории).

Студент самостоятельно:

- проектирует BPMN 2.0-схему (исполняемую);
- реализует каждый этап;
- интегрируется с API МойСклад (заглушка);
- реализует отмену на разных этапах и компенсацию;
- обеспечивает идемпотентность и работу нескольких инстансов приложения;
- обрабатывает повтор задач и технические сбои;
- пишет автоматические тесты процесса.

**Инфраструктура (заглушка, сиды, эмуляция сбоев) уже дана. BPMN, JavaDelegate этапов заказа, API управления процессом и компенсацию пишет студент — готового решения в репозитории нет.**

## 3. Бизнес-сценарий

**Название процесса:** «Обработка заказа покупателя с резервированием и отгрузкой».

Запуск: REST API приложения по `orderId` (UUID заказа в заглушке, см. `RemapStubIds`).

## 4. Восемь этапов

### Этап 1 — получение и проверка заказа

| | |
|---|---|
| **Вход** | `orderId` |
| **Действия** | Получить заказ через SDK; проверить существование, наличие позиций, корректность количеств, допустимость обработки; **запретить** повторный запуск активного процесса для того же заказа |
| **Результат** | Заказ принят в обработку либо бизнес-ошибка |

### Этап 2 — проверка остатков

| | |
|---|---|
| **Вход** | Позиции заказа |
| **Действия** | Получить доступные остатки (`report/stock/all` и/или данные заказа); учесть резервы; при нехватке — **ожидание** с повторной проверкой по таймеру, лимит ожидания, возможность отмены во время ожидания |
| **Результат** | Остатков достаточно / ожидание / таймаут / отмена |

Элементы BPMN (таймер, gateway и т.д.) выбирает студент.

### Этап 3 — резервирование

| | |
|---|---|
| **Действия** | Установить `reserve` на позициях заказа через Remap (PUT позиции / заказа); зафиксировать факт резервирования; **идемпотентность**: повтор Service Task не должен увеличивать резерв повторно; при отмене — освобождение (`reserve → 0` или эквивалент) |
| **Результат** | Резерв установлен |

### Этап 4 — ожидание подтверждения отгрузки

| | |
|---|---|
| **Действия** | Ждать внешнее решение через REST: **подтвердить** или **отклонить**; состояние ожидания переживает рестарт; таймаут; идемпотентность повторного подтверждения; отмена возможна; при отклонении — компенсация |
| **Результат** | Подтверждено / отклонено / таймаут / отмена |

### Этап 5 — создание отгрузки (demand)

| | |
|---|---|
| **Действия** | Создать `demand`, связать с заказом, сохранить id; **не** создавать дубликаты при retry Camunda |
| **Обязательный сценарий** | Запрос ушёл → отгрузка создана в API → ответ потерян (`LOSE_RESPONSE` заглушки) → Camunda повторяет задачу → в итоге **один** документ |

### Этап 6 — проверка отгрузки

| | |
|---|---|
| **Действия** | Получить отгрузку и позиции; сверить с заказом (товары, количества, допустимое состояние); временные ошибки — retry; неисправимая бизнес-ошибка — завершение с компенсацией |

### Этап 7 — подтверждение отгрузки (проведение)

| | |
|---|---|
| **Действия** | Финальное проведение (`applicable=true` у demand); идемпотентность; обработка технических ошибок |
| **Важно** | После успеха — **точка необратимости**: автоматическая отмена процесса **не** допускается |

### Этап 8 — завершение

| | |
|---|---|
| **Действия** | Зафиксировать `COMPLETED`, id документов, итоговый статус; результат доступен через API |

## 5. BPMN 2.0

Студент создаёт **исполняемую** схему для Camunda 7.24 Embedded.

Готовую BPMN XML / готовую раскладку элементов репозиторий **не** предоставляет — структура на вашей ответственности.

### Элементы, которые нужно уметь обосновать

| Элемент | Назначение | Когда применять в этом процессе |
|---|---|---|
| **Start Event** | Старт обработки | Запуск по REST с `orderId` / business key |
| **Service Task** | Автоматические шаги (SDK, проверки) | Этапы 1–3, 5–8 |
| **Exclusive Gateway** | Ветвление по условиям | Достаточно ли остатков, подтверждено/отклонено, ошибка |
| **Intermediate Timer Catch Event** | Отложенное продолжение | Повтор проверки остатков |
| **Intermediate Message Catch Event** | Ожидание внешнего сигнала | Подтверждение / отклонение отгрузки |
| **Boundary Timer Event** | Таймаут на активности | Таймаут ожидания остатков / подтверждения |
| **Interrupting Event Subprocess** | Реакция на отмену | Запрос отмены с REST |
| **Compensation Handler** | Откат выполненных шагов | Снятие резерва, удаление черновика demand |
| **End Event** | Завершение | `COMPLETED`, `CANCELLED`, ошибки, `COMPENSATION_FAILED` |

Допустимы дополнительные элементы при обосновании.

Схема должна покрывать: успешный путь, ожидание остатков, ожидание подтверждения, отклонение, отмену, технические ошибки, retry, компенсацию.

- что делает каждый этап;

- где альтернативные пути и ожидания;
- где компенсация;
- какими сценариями процесс завершается.

## 6. Отмена и компенсация

Отмена инициируется REST API. Простое `deleteProcessInstance` **не** считается корректной отменой.

Требования:

- отмена на разных этапах;
- повторная отмена идемпотентна;
- учёт текущего состояния;
- компенсация уже выполненного;
- после старта отмены новые бизнес-операции не стартуют;
- работает после рестарта и при нескольких инстансах.

| Этап | Поведение |
|---|---|
| До резервирования | Завершение без компенсации |
| После резервирования | Освободить резерв |
| Ожидание подтверждения | Прервать ожидание + освободить резерв |
| После создания отгрузки (черновик) | Удалить/отменить draft demand + освободить резерв |
| Во время проверки отгрузки | Прервать + компенсация |
| Во время подтверждения | Корректно разрешить гонку с отменой |
| После финального проведения | **Отказ** в автоматической отмене |
| После завершения | Повторная отмена не меняет состояние |

Компенсация:

- только реально выполненные операции;
- не выполняется повторно без нужды;
- сохраняет свой результат;
- поддерживает retry при технических сбоях;
- не теряется при рестарте.

Если компенсация упала — процесс **не** должен ошибочно получить `CANCELLED`. Предусмотрите диагностируемый статус, например `COMPENSATION_FAILED`, и способ восстановления.

Изучите ограничения компенсации Camunda 7 (области обработчиков, транзакции).

### Конкурентная отмена (обязательный сценарий)

1. Инстанс A начинает резервирование.  
2. Инстанс B получает запрос отмены.  
3. A успешно завершает резервирование.  
4. B инициирует завершение.  
5. Резерв **обязан** быть освобождён.

Недопустимо: процесс `CANCELLED`, а резерв остался.

## 7. Нефункциональные требования

### Идемпотентность

Меняющие операции идемпотентны с точки зрения процесса: резерв, снятие резерва, создание demand, проведение, компенсация.

Повтор Service Task не создаёт дублей. Локальный `synchronized` / флаг в памяти JVM **недостаточен** — нужен устойчивый учёт результатов (БД).

### Несколько инстансов

Общая PostgreSQL + общий Camunda persistence.

1. Один заказ — не более одного **активного** экземпляра процесса.  
2. Конкурентные старты обрабатываются корректно.  
3. Job Executor / acquisition / exclusive jobs / optimistic locking — понимать и использовать осознанно.  
4. `exclusive jobs` **не** заменяют уникальность процесса по заказу и идемпотентность внешних вызовов.  
5. Локальные блокировки — не единственный механизм синхронизации.

### Устойчивость к сбоям

Рестарт приложения, падение инстанса, 429/5xx/timeout заглушки, retry задачи, **потеря ответа после успешной операции** (`LOSE_RESPONSE`).

Важно: успешный внешний вызов **не** гарантирует, что Camunda уже сохранила его результат.

### Повторные попытки

Разделяйте бизнес-ошибки, временные технические и неисправимые. Для временных — ограниченные retry с задержкой (механизмы Camunda 7), затем диагностируемое состояние.

### Транзакционность

Транзакция БД приложения **не** охватывает HTTP к МойСклад. Определите границы, где нужны `asyncBefore` / `asyncAfter`, как восстанавливаться после частично успешных операций. Допустимы Saga / outbox / иные обоснованные паттерны (не все сразу).

### Наблюдаемость

Минимум в переменных/логах/API статуса: `orderId`, `processInstanceId`, `businessKey`, этап, статус, id отгрузки, причина ошибки, число попыток, статус компенсации. Логи должны позволять трассировать один процесс через несколько инстансов.

## 9. Тестирование студенческого решения

Использовать реальный Camunda Engine и **заглушку** (не боевой аккаунт МойСклад). Предпочтительно Testcontainers (как в существующих тестах проекта).

### Функциональные

Успех; недостаток остатка; пополнение и продолжение; таймаут ожидания остатков; подтверждение; отклонение; ошибка проверки отгрузки; завершение `COMPLETED`.

### Отмена

До/после резерва; во время ожидания; после создания demand; во время проверки; гонка с операцией; отказ после необратимости; повторная отмена; ошибка компенсации и её повтор.

Повторный старт; повтор резерва / создания demand / проведения / снятия резерва; потеря ответа после успеха.

### Несколько инстансов

Одновременный старт одного заказа; конкурентный резерв; конкурентная отмена; jobs на разных инстансах; падение одного инстанса и продолжение другим. Общая БД; **не** заменять полноценный распределённый сценарий только потоками в одной JVM.


```java
ApiClient api = new ApiClient("localhost:8080", false, "any@company", "password");
CustomerOrder order = api.entity().customerorder()
```
