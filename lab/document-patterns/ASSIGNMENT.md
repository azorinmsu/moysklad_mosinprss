# Задание: обработка ERP-документов с помощью паттернов проектирования

## Цель

Спроектировать и реализовать расширяемую систему обработки складских документов МойСклад:
создание, заполнение позиций, проверка, проведение, формирование движений, отмена проведения,
смена статусов, дополнительная обработка, история операций и уведомления.

**Главное требование:** добавление нового типа документа не должно требовать переписывания
центрального сервиса обработки (`DocumentService`).

Пакет: `ru.moysklad.intern.documentpatterns` (модуль `intern`). Стек: Java 27, Maven, JUnit 5, AssertJ.
Spring-контекст, БД, Kafka и Camunda не нужны.

## Типы документов

| Документ | Класс | `DocumentsType` | Влияние на остатки |
|---|---|---|---|
| Приёмка | `AcceptanceDocument` | `GOODS_ACCEPTANCE` | Приход на склад-получатель |
| Отгрузка | `ShipmentDocument` | `SHIPMENT` | Расход со склада-источника |
| Перемещение | `TransferDocument` | `SHIFT` | Расход с источника и приход на получатель, атомарно |

`MACHINING` и `MAKE` в обязательную часть не входят (см. «Задания повышенной сложности»).

### Бизнес-правила

**Приёмка:** указан склад-получатель; есть хотя бы одна позиция; количество положительное; проведение увеличивает остаток.

**Отгрузка:** указан склад-источник; товара достаточно; проведение уменьшает остаток; отрицательный остаток недопустим.

**Перемещение:** указаны оба склада; склады различаются; на источнике достаточно товара; проведение уменьшает остаток
на источнике и увеличивает на получателе; оба движения применяются атомарно.

**Общие:** нельзя провести пустой документ; нельзя провести проведённый документ повторно; нельзя менять позиции
проведённого документа; отмена проведения восстанавливает остатки; повторная отмена не меняет остатки;
ошибочная операция не оставляет частично применённых движений.

## Как работать

1. Прочитайте [ARCHITECTURE.md](ARCHITECTURE.md): там маршрут выполнения и UML каждого паттерна.
2. Запустите тесты лабораторной ([TESTING.md](TESTING.md)) — 22 инфраструктурных теста должны пройти.
3. Выполняйте части по порядку: каждая следующая опирается на предыдущие.
4. Для каждой части: снимите `@Disabled` с тестов-заготовок, напишите проверки по подсказкам `TODO`,
   убедитесь, что тест падает, затем реализуйте методы с `TODO` и добейтесь прохождения.
5. Не меняйте готовую инфраструктуру (классы без `TODO`). Если кажется, что без этого не обойтись, — обсудите с преподавателем.

Методы-заготовки бросают `UnsupportedOperationException("TODO")`. После реализации в коде не должно остаться `TODO`.

## Часть 1. Factory Method / Abstract Factory — создание документов (10 баллов)

**Теория.** Factory Method определяет в базовом классе алгоритм создания, а выбор конкретного класса продукта
делегирует подклассам через переопределяемый «фабричный метод». Abstract Factory создаёт *семейство* согласованных
объектов, не указывая их конкретных классов. Simple Factory (метод с `switch` по типу) — не GoF-паттерн.

**Сценарий МойСклад.** Для каждого вида документа нужны согласованные объекты: сам документ, правило расчёта
движений и обработчик проведения. Перемещение нельзя проводить обработчиком отгрузки.

**Проблема без паттерна.** `switch (type)` в сервисе создаёт документы, стратегии и обработчики в разных местах.
Новый тип требует правки всех таких `switch`; легко создать несогласованную пару «документ — обработчик».

**Что реализовать.** `DocumentFactory` — одновременно:

- *Factory Method*: `createDocument(id, moment)` (общий алгоритм) использует фабричный метод `newDocument(...)`;
- *Abstract Factory*: подкласс создаёт семейство своего типа — `newDocument`, `createMovementStrategy`, `createProcessor`.

`DocumentFactoryRegistry` (готов) — лишь поиск фабрики по типу, по сути Simple Factory; он не заменяет Factory Method.

**Методы с `TODO`.**

- `factory.DocumentFactory#createDocument`
- `AcceptanceDocumentFactory`, `ShipmentDocumentFactory`, `TransferDocumentFactory`: `newDocument`, `createMovementStrategy`, `createProcessor`

**Как выполнить.** В `createDocument` проверьте аргументы (`IllegalArgumentException`), вызовите фабричный метод,
убедитесь, что подкласс вернул документ правильного типа в статусе `DRAFT` (`IllegalStateException` — ошибка реализации
фабрики), верните документ. Конкретные фабрики создают объекты своего семейства; обработчик получает стратегию
из `createMovementStrategy()` той же фабрики.

**Тесты** (`factory/DocumentFactoryTest`): создание приёмки, отгрузки, перемещения; тип документа; начальный статус;
обязательные поля; согласованность семейства; обнаружение ошибочного подкласса.

**Ожидаемый результат.** Каждая фабрика создаёт черновик своего типа с заданными `id` и датой и согласованные
стратегию и обработчик.

**Критерии приёмки.** `createDocument` не содержит `switch`/`instanceof` по типам; новый тип документа добавляется
новым подклассом фабрики; 8 тестов проходят.

**Почему это полезно при расширении ERP.** Новый документ (например, «Списание») = новый подкласс документа,
стратегия, обработчик и фабрика, зарегистрированная в списке фабрик `DocumentService`. Ни сервис, ни существующие фабрики,
ни валидаторы не меняются (Open/Closed Principle).

## Часть 2. Strategy — расчёт движений (15 баллов)

**Теория.** Strategy инкапсулирует взаимозаменяемые алгоритмы за общим интерфейсом; клиент выбирает алгоритм,
не зная его деталей.

**Сценарий МойСклад.** Каждый тип документа по-своему превращает позиции в движения:

```text
Приёмка 10 X на A        →  A / X: +10
Отгрузка 7 X с A         →  A / X: -7
Перемещение 5 X с A на B →  A / X: -5,  B / X: +5
```

**Проблема без паттерна.** Один метод с `if (type == ...)` растёт с каждым типом, смешивает расчёт с записью в БД
и плохо тестируется.

**Что реализовать.** `AcceptanceMovementStrategy`, `ShipmentMovementStrategy`, `TransferMovementStrategy`.

**Методы с `TODO`.** `calculateMovements(ErpDocument)` в трёх стратегиях.

**Как выполнить.** Для каждой позиции создайте `StockMovement` (документ, товар, склад, партия, дельта со знаком).
Сохраняйте порядок позиций; для перемещения — пару «расход, приход» на позицию. Верните неизменяемый список.
**Стратегия только вычисляет** и не имеет доступа к хранилищу: так расчёт можно переиспользовать для проверки
остатков и предпросмотра, а выполнение остаётся атомарным в одном месте.

**Тесты** (`strategy/StockMovementStrategyTest`): знак движения; склад; количество; несколько позиций;
перемещение между складами; партия; отсутствие изменений хранилища.

**Ожидаемый результат.** Движения совпадают с таблицей выше; хранилище не меняется.

**Критерии приёмки.** В стратегиях нет обращений к хранилищу и проверок остатков; 6 тестов проходят.

## Часть 3. Chain of Responsibility — проверки документа (15 баллов)

**Теория.** Запрос проходит по цепочке обработчиков; каждый решает свою часть задачи и передаёт запрос дальше
или прерывает обработку.

**Сценарий МойСклад.** Перед проведением выполняются последовательные проверки.

| Проверка из постановки | Где выполняется | Код ошибки |
|---|---|---|
| 1. Документ существует | шаг 0 `AbstractDocumentProcessor#process` | `DOCUMENT_REQUIRED` |
| 2. Допустимый статус | State на шаге 1 `process` (единственный владелец правил жизненного цикла) | `ALREADY_POSTED`, `ALREADY_CANCELLED` |
| 3. Есть товарные позиции | `PositionValidator` | `EMPTY_DOCUMENT` |
| 4. Количество положительное | `QuantityValidator` | `INVALID_QUANTITY` |
| 5. Склады указаны корректно | `WarehouseValidator` | `MISSING_SOURCE_WAREHOUSE`, `MISSING_TARGET_WAREHOUSE`, `SAME_WAREHOUSES` |
| 6. Для расхода хватает остатков | `StockAvailabilityValidator` | `INSUFFICIENT_STOCK` |

Статус намеренно не проверяется отдельным звеном: это правило уже выражено паттерном State, дублирование
привело бы к двум источникам истины.

**Проблема без паттерна.** Большой метод с десятком `if`; добавление правила требует правки центрального кода;
порядок проверок неявный; невозможно переиспользовать отдельное правило.

**Что реализовать.** Четыре звена и сборку стандартной цепочки. Механика связывания (`AbstractDocumentValidator#validate`,
`linkWith`, `DocumentValidationChain.of`) готова.

**Методы с `TODO`.**

- `PositionValidator#check`, `QuantityValidator#check`, `WarehouseValidator#check`, `StockAvailabilityValidator#check`
- `DocumentValidationChain#defaultChain`

**Как выполнить.** Одно звено — одно правило; нарушение — `DocumentValidationException` с кодом (исключение прерывает
цепочку). `WarehouseValidator` узнаёт требования к складам у документа (`requiresSourceWarehouse()`,
`requiresTargetWarehouse()`), а не через `switch` по типу. `StockAvailabilityValidator` работает с плановыми движениями
`context.plannedMovements()`: суммирует расход по ключу «товар + склад + партия» и сравнивает с `availableQuantity`.
Порядок: дешёвые структурные проверки раньше, проверка остатков (требует расчёта движений) — последней.

**Тесты** (`validation/DocumentValidationChainTest`): пустой документ; некорректное количество; отсутствующий склад;
совпадающие склады перемещения; недостаточный остаток (в т.ч. сумма двух позиций); прекращение цепочки после ошибки;
успешная проверка; порядок звеньев; расширение цепочки новым звеном.

**Ожидаемый результат.** Каждое нарушение даёт свой код; после первой ошибки следующие звенья не вызываются;
на пустом документе движения даже не рассчитываются.

**Критерии приёмки.** Звенья не знают о типах документов; новое правило добавляется новым классом; 9 тестов проходят.

## Часть 4. Template Method — проведение документа (10 баллов)

**Теория.** Базовый класс фиксирует скелет алгоритма в `final`-методе, подклассы переопределяют отдельные шаги
(«крючки»), но не порядок.

**Сценарий МойСклад.** Проведение любого документа проходит одни и те же шаги, отличаются только специфичные
проверки и расчёт движений.

```text
0. document == null              → DOCUMENT_REQUIRED
1. new DocumentContext(doc).post()   — State: можно ли провести (переход только планируется)
2. validationChain.validate(...) + validateSpecific(doc)
3. movements = context.plannedMovements()   — стратегия вызвана один раз
4. stockRepository.apply(movements)        — атомарно, хранилище повторно проверит остатки
5. lifecycle.commit()                       — статус POSTED только после успешного шага 4
6. document.recordPostedMovements(movements)
7. publish(DOCUMENT_POSTED)                 — после фиксации
ошибка на шагах 1–6 → publish(DOCUMENT_PROCESSING_FAILED) и проброс исключения
```

**Проблема без паттерна.** Каждый тип документа копирует алгоритм проведения; исправление ошибки (например,
порядка «статус — событие») нужно вносить в три места.

**Что реализовать.** Общий алгоритм `process` и крючки трёх обработчиков.

**Методы с `TODO`.**

- `AbstractDocumentProcessor#process`
- `AcceptanceProcessor`, `ShipmentProcessor`, `TransferProcessor`: `validateSpecific`, `calculateMovements`

Специфичные правила: у приёмки не должно быть склада-источника (`UNEXPECTED_SOURCE_WAREHOUSE`), у отгрузки —
склада-получателя (`UNEXPECTED_TARGET_WAREHOUSE`), в перемещении не должно быть двух позиций с одной парой
«товар + партия» (`DUPLICATE_POSITION`). `calculateMovements` делегирует стратегии.

**Тесты** (`processing/DocumentProcessorTest`): порядок шагов; успешное проведение; ошибка валидации; ошибка
применения движений; отсутствие частичных изменений; повторное проведение; специфичные правила; `null` и однократный
расчёт движений.

**Ожидаемый результат.** После успеха — `POSTED`, остатки изменены, событие опубликовано; после любой ошибки —
прежний статус, прежние остатки, только событие ошибки.

**Критерии приёмки.** `process` — `final` и единственное место с порядком шагов; подклассы не дублируют общий
алгоритм; 8 тестов проходят.

## Часть 5. Decorator — дополнительные операции (10 баллов)

**Теория.** Decorator оборачивает объект тем же интерфейсом и добавляет поведение до/после делегирования. Обёртки
комбинируются во время выполнения, в отличие от наследования, где комбинации фиксируются иерархией классов.

**Сценарий МойСклад.** К проведению нужно добавить логирование и аудит, не меняя обработчики.

**Проблема без паттерна.** Логирование и аудит вписываются в каждый обработчик или появляются подклассы
`LoggingAuditedShipmentProcessor` и т.п. — комбинаторный рост.

**Что реализовать.** `LoggingDecorator`, `AuditDecorator`; дополнительно — `TimingDecorator`.

**Методы с `TODO`.** `LoggingDecorator#execute`, `AuditDecorator#execute`, `TimingDecorator#execute` (дополнительно).

**Как выполнить.** Декоратор обязательно делегирует `delegate.execute(document)`. Логирование пишет начало,
успех (с итоговым статусом) или ошибку и пробрасывает **то же** исключение. Аудит фиксирует фактический результат:
`SUCCESS` со статусом после операции или `FAILURE` с кодом ошибки и неизменённым статусом.

**Тесты** (`decorator/DocumentDecoratorTest`): базовая операция; логирование; аудит; комбинация в любом порядке;
ошибка основной операции; корректность аудита ошибки; дополнительно — измерение времени.

**Ожидаемый результат.** Декораторы прозрачны для бизнес-результата; ошибка не записывается как успех.

**Критерии приёмки.** Обработчики не знают о логировании и аудите; 6 обязательных тестов проходят (+1 дополнительный).

## Часть 6. Command — проведение и отмена (10 баллов)

**Теория.** Command превращает запрос в объект с контекстом выполнения. Объект можно передать исполнителю,
записать в историю, повторить или отклонить как дубликат.

**Сценарий МойСклад.** «Провести документ» и «Отменить проведение» — бизнес-операции с идентификатором
(`operationId`): повторная доставка той же операции (повтор HTTP-запроса, повторное сообщение) не должна
изменить остатки дважды.

**Проблема без паттерна.** Методы сервиса не хранят контекст операции; идемпотентность и история размазаны по коду.

**Что реализовать.**

- `PostDocumentCommand#execute` — запуск операции проведения (обработчик, обёрнутый декораторами);
- `UnpostDocumentCommand#execute` — отмена проведения: State, **обратные движения** из
  `document.getPostedMovements()`, атомарное применение, `commit`, событие `DOCUMENT_UNPOSTED`;
- `DocumentCommandExecutor#execute` — идемпотентность по `operationId` и история операций.

**Как выполнить.** Отмена — не удаление документа и не «undo» в памяти: в журнал остатков добавляются новые
обратные движения, документ получает статус `CANCELLED`. Хранилище учитывает текущие остатки: если товар уже ушёл
со склада-получателя перемещения, отмена невозможна (`INSUFFICIENT_STOCK`), статус остаётся `POSTED`.
Исполнитель: успешный `operationId` повторно не выполняется (`SKIPPED_DUPLICATE`); неуспешный можно повторить;
проверка и выполнение атомарны относительно других потоков. Универсальный откат произвольных команд не требуется.

**Тесты** (`command/DocumentCommandTest`): проведение; отмена; повторное проведение; повторная отмена; отмена черновика;
отмена при недостаточном остатке; сохранение истории; конкурентный повтор одной операции.

**Ожидаемый результат.** Нет двойного изменения остатков; история движений содержит прямые и обратные движения;
история исполнителя — все попытки с результатом.

**Критерии приёмки.** 8 тестов проходят; отмена реализована обратными движениями.

## Часть 7. State — жизненный цикл документа (10 баллов)

**Теория.** State выносит поведение, зависящее от состояния, в отдельные объекты-состояния; объект делегирует им
операции, и смена состояния меняет поведение без `switch` в каждом методе.

```text
DRAFT --post--> POSTED --unpost--> CANCELLED
```

**Сценарий МойСклад.** Черновик можно провести; проведённый документ — отменить; повторно провести проведённый
документ нельзя; отменить черновик «как проведённый» нельзя.

**`CANCELLED` в учебной модели** — «проведение отменено»: движения сторнированы, документ сохранён и доступен в истории.
Это **не удаление** документа (удалённый документ исчезает из учёта) и **не бизнес-отмена заказа**
(отмена заказа покупателя — смена статуса заказа, которая может вообще не затрагивать остатки).

**Проблема без паттерна.** `switch (status)` в каждом сервисе, который проводит или отменяет документ; правила
переходов дублируются и расходятся.

**Что реализовать.** `DraftState`, `PostedState`, `CancelledState`. Контекст `DocumentContext` (готов) реализует
двухфазную смену статуса: состояние только *планирует* переход (`transitionTo`), а применяет его `commit()` после
успешной операции.

**Методы с `TODO`.** `post` и `unpost` в трёх состояниях.

**Тесты** (`state/DocumentStateTest`): DRAFT → POSTED; POSTED → CANCELLED; повторное проведение; отмена черновика;
повторная отмена; сохранение статуса при ошибке; соответствие состояний статусам.

**Ожидаемый результат.** Недопустимые переходы дают `DocumentStateException` с кодом, статус меняется только в `commit()`.

**Критерии приёмки.** Правила переходов есть только в классах состояний; 7 тестов проходят.

## Часть 8. Observer — события документов (5 баллов)

**Теория.** Observer позволяет субъекту оповещать подписчиков об изменениях, не зная их конкретных классов.

**Сценарий МойСклад.** После проведения нужно уведомить менеджера и записать событие в журнал; завтра появится
интеграция с бухгалтерией. События: `DOCUMENT_CREATED`, `DOCUMENT_POSTED`, `DOCUMENT_UNPOSTED`, `DOCUMENT_PROCESSING_FAILED`.

**Проблема без паттерна.** Обработчик напрямую вызывает почту, журнал и интеграции; падение почты «роняет» проведение.

**Что реализовать.** `DocumentEventPublisher` (`subscribe`, `unsubscribe`, `publish`), `AuditDocumentListener`,
`NotificationDocumentListener`.

**Как выполнить.** Публикатор доставляет события по порядку подписки, перехватывает исключения подписчиков
(сохраняет `DeliveryFailure`) и не пробрасывает их: операция уже зафиксирована. Подписчики не дублируют записи
и уведомления для того же `eventId`. Уведомления — о проведении, отмене и ошибке, но не о создании.

**Порядок в учебном in-memory режиме:** остатки применены → статус изменён → движения зафиксированы → событие опубликовано.

**Надёжная доставка в реальной системе.** Синхронный Observer не гарантирует доставку: процесс может упасть после
фиксации транзакции, но до уведомления, или уведомление уйдёт, а транзакция откатится. В БД используют
**transactional outbox**: событие записывается в таблицу outbox в той же транзакции, что и изменения документа,
а отдельный процесс публикует его в брокер с повторами (в проекте так устроен `outbox_event`).

**Тесты** (`observer/DocumentObserverTest`): публикация; несколько подписчиков; нет события при неуспехе;
ошибка подписчика; повторная операция; корректные типы событий и уведомления.

**Критерии приёмки.** Обработчики не знают о конкретных подписчиках; 6 тестов проходят.

## Часть 9. Builder — создание документов (5 баллов)

**Теория.** Builder отделяет пошаговое конструирование сложного объекта от его представления и проверяет
целостность в `build()`.

```java
ErpDocument document = DocumentBuilder.acceptance()
        .id(UUID.randomUUID())
        .targetWarehouse(warehouse)
        .addPosition(productA, new BigDecimal("10"))
        .addPosition(productB, new BigDecimal("5"))
        .build();
```

**Проблема без паттерна.** Цепочки сеттеров после конструктора, документ существует в незавершённом состоянии,
обязательные поля легко забыть.

**Что реализовать.** Методы `DocumentBuilder`: `id`, `moment`, `sourceWarehouse`, `targetWarehouse`, `addPosition` (×2), `build`.

**Как выполнить.** Builder накапливает параметры; `build()` проверяет обязательные поля (`id`; склады, которые
требует тип документа — `IllegalStateException`), берёт текущее время, если дата не задана, создаёт документ
**через фабрику** и переносит в него склады и позиции. Положительность количества — правило цепочки, не builder.
Каждый `build()` возвращает новый независимый документ.

**Тесты** (`builder/DocumentBuilderTest`): приёмка; отгрузка; перемещение; несколько позиций; отсутствие обязательного
поля; независимость созданных объектов; дата по умолчанию.

**Критерии приёмки.** Builder не создаёт документы через `new`, а использует фабрику; 7 тестов проходят.

## Часть 10. Объединение паттернов — `DocumentService` (10 баллов вместе с тестами)

**Что реализовать.** Конструктор `DocumentService`, `create`, `post(document, operationId)`, `unpost(document, operationId)`.

**Единый маршрут** (без дублирующих вызовов):

```text
create : Factory (через реестр) → Builder → DOCUMENT_CREATED
post   : Command → Executor → AuditDecorator → LoggingDecorator → Template Method
           [ State → Chain → Strategy → атомарное применение → commit → Observer ]
unpost : Command → Executor → UnpostDocumentCommand
           [ State → обратные движения → атомарное применение → commit → Observer ]
```

Сервис не вызывает цепочку, State и публикацию событий проведения сам — это делает обработчик. В сервисе нет
`switch` по типу: обработчики создаются фабриками в конструкторе один раз и хранятся по типу документа.

**Сквозной сценарий** (`DocumentWorkflowTest#fullDocumentLifecycle`):

```text
Начальные остатки: A: X=20, Y=10; B: X=0, Y=0
1. Приёмка 10 X на A              → A/X = 30
2. Отгрузка 7 X с A               → A/X = 23
3. Перемещение 5 X с A на B       → A/X = 18, B/X = 5
4. Отмена проведения перемещения  → A/X = 23, B/X = 0
5. Отгрузка 100 X с A             → INSUFFICIENT_STOCK; остатки не изменились;
                                     документ не POSTED; нет события DOCUMENT_POSTED
```

**Тесты** (`DocumentWorkflowTest`): сквозной сценарий; отсутствие двойного изменения остатков; неподдерживаемый
тип `MAKE`; согласованность аудита, истории и событий.
