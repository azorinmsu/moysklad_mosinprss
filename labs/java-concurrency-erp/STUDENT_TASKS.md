# Лабораторная работа. Многопоточность Java в контуре ERP

## Цель

Найти и исправить 15 дефектов конкурентного доступа в упрощённой модели МойСклад и реализовать 4 синхронизатора с заданным контрактом.

Исправление оценивается по наблюдаемому поведению и бизнес-инвариантам. Подходит любое корректное решение: `synchronized`, `Lock`, атомарные переменные, конкурентные коллекции или другой механизм, если тесты группы `bug` и `baseline` проходят. Тесты не требуют конкретную конструкцию языка.

## Что уже нужно уметь

Java Core, Spring Boot, основы JMM и пакета `java.util.concurrent`: гонки, видимость, взаимное исключение, взаимная блокировка, `Lock`, `ReadWriteLock`, `Condition`, `Semaphore`, `CountDownLatch`, `CompletableFuture`, безопасная публикация, `ThreadLocal`.

## Предметная область

Один процесс хранит данные в памяти.

| Сервис | Ответственность |
|---|---|
| `InventoryService` | начальные остатки, приход, списание, кэш остатка |
| `ReservationService` | резерв под заказ покупателя |
| `SalesOrderService` | заказ и счётчик заказов покупателя |
| `PurchaseOrderService` | приход по закупке |
| `ShipmentService` | отгрузка и ожидание поступления |
| `StockTransferService` | перемещение между складами |
| `PriceService` | цена и политика скидок |
| `ReportService` | остатки, обороты, свод по складам |
| `EventProcessingService` | проведение движения |
| `ReportRefreshTask`, `ExternalSyncGateway`, `OrderEventProcessor` | фоновый пересчёт, лимит внешней синхронизации, контекст организации |

Сущности: `Product`, `Warehouse`, `StockBalance`, `Reservation`, `SalesOrder`, `Shipment`, `PurchaseOrder`, `StockTransfer`, `Price`, `StockMovement`.

Складской инвариант, если в задании не сказано иное: количество не отрицательное; зарезервировано не больше количества; сумма остатков при перемещении сохраняется; успешная операция видна следующим операциям.

## Как запускать

```bash
cd labs/java-concurrency-erp
./mvnw test
./mvnw test -Dgroups=baseline
./mvnw test -Dgroups=bug
./mvnw test -Dgroups=synchronizer
./mvnw -Dtest=Bug01Test test
./mvnw -Dtest=CustomSemaphoreTest test
./mvnw spring-boot:run
```

JDK 21+. `./mvnw test` в начале работы падает: дефекты ещё не исправлены, синхронизаторы не написаны. Группа `baseline` должна проходить и до, и после исправлений.

`SyncPoint` — тестовый зонд. Не удаляйте его вызовы. Оставляйте их в тех же логических точках: после чтения разделяемого состояния и до записи, между захватами блокировок складов, в итерации отчёта, в публикации политики цен. В обычном запуске зонд ничего не ждёт.

Не заменяйте потоки циклом в одном потоке. Не подключайте базу и API МойСклад: синхронизация здесь не про уровни изоляции СУБД.

После своих правок не должно оставаться рабочих потоков. Пулы в тестах останавливаются через `shutdownNow` и `awaitTermination`.

## Пятнадцать сценариев

Для каждого сценария ниже указаны бизнес-ситуация, симптом, инвариант и тест. Причину и способ исправления нужно установить по коду и падающему тесту.

### BUG-01. Резерв последних единиц

Два покупателя одновременно резервируют последнюю единицу товара.

Симптом: оба резерва принимаются либо остаток резерва не сходится с числом принятых резервов.

Инвариант: успешных резервов не больше, чем доступно на момент операции; `reserved` равен сумме количеств принятых резервов.

Тест: `Bug01Test`.

### BUG-02. Остановка пересчёта отчёта

Фоновый поток пересчитывает отчёт и должен завершиться по сигналу остановки.

Симптом: поток продолжает работу после сигнала дольше допустимого ожидания.

Инвариант: после запроса остановки поток завершается в пределах таймаута теста.

Тест: `Bug02Test`. Проверка вынесена в отдельный процесс, чтобы зависший цикл не оставался в JVM тестов. Перед сигналом процесс даёт JIT время скомпилировать цикл: на этой проверке пауза нужна из-за модели памяти, а не как способ «подождать планировщик». Если цикл не видит флаг, процесс завершается с ненулевым кодом. Ограничение: на некоторых JVM без оптимизации цикл может остановиться и без исправления модели памяти; эталонная проверка рассчитана на HotSpot с компиляцией цикла.

### BUG-03. Списание остатка

Два потока списывают товар, которого хватает только на одну операцию.

Симптом: обе операции проходят, итоговое количество не равно начальному минус успешные списания.

Инвариант: ровно одна из двух операций на 3 единицы при остатке 5 успешна, остаток равен 2 и не отрицателен.

Тест: `Bug03Test`.

### BUG-04. Встречные перемещения

Один поток перемещает товар со склада A на B, другой — с B на A.

Симптом: обе операции не завершаются. Тест распознаёт взаимную блокировку через `ThreadMXBean` и не ждёт бесконечно.

Инвариант: оба перемещения завершаются, сумма остатков A и B сохраняется, количества не отрицательны.

Тест: `Bug04Test`.

### BUG-05. Повторная отгрузка после ошибки

Отгрузка с некорректным количеством завершается исключением. Следующая отгрузка того же сервиса должна выполниться.

Симптом: следующая отгрузка не начинается в отведённое время.

Инвариант: после исключения другие вызовы отгрузки выполняются, остаток уменьшается только успешной отгрузкой.

Тест: `Bug05Test`.

### BUG-06. Параллельное обновление оборотов

Несколько потоков добавляют оборот одного склада, пока отчёты читают итог.

Симптом: общий оборот меньше суммы переданных значений.

Инвариант: итог и оборот склада равны сумме всех учтённых сумм.

Тест: `Bug06Test`.

### BUG-07. Кэш остатка

Несколько потоков увеличивают кэш одного товара.

Симптом: в кэше теряется часть прибавлений.

Инвариант: значение кэша равно сумме прибавлений. Тест проверяет число, а не внутреннюю порчу таблицы.

Тест: `Bug07Test`.

### BUG-08. Счётчик заказов покупателя

Несколько потоков регистрируют заказы одного покупателя.

Симптом: счётчик меньше числа регистраций.

Инвариант: счётчик равен числу вызовов регистрации для этого покупателя.

Тест: `Bug08Test`.

### BUG-09. Отчёт по движениям

Один поток суммирует движения, другой в это время добавляет движение.

Симптом: расчёт падает или возвращает сумму, которая не совпадает ни с одним согласованным снимком списка.

Инвариант: исключения нет; сумма равна снимку списка до добавления или после него.

Тест: `Bug09Test`. Зонд стоит внутри обхода уже снятой последовательности. Запись нового движения не должна ждать этот обход и не должна его рвать.

### BUG-10. Отгрузка по поступлению

Поток ждёт бумагу. На склад сначала приходит другой товар, затем бумага.

Симптом: отгрузка бумаги выполняется из-за чужого прихода, остаток уходит в минус либо заказ не исполняется после реального прихода.

Инвариант: чужой приход не закрывает ожидание; после прихода нужного товара отгрузка проходит, остаток не отрицателен.

Тест: `Bug10Test`. Пробуждение управляемое: это приход другого товара, а не случайная пауза.

### BUG-11. Лимит внешней синхронизации

Шлюз пускает не больше заданного числа одновременных вызовов. Вызов, который не получил разрешение, не должен менять лимит.

Симптом: одновременно выполняются больше операций, чем позволяет лимит.

Инвариант: максимум одновременных выполнений не выше лимита; после серии вызовов число разрешений возвращается к исходному.

Тест: `Bug11Test`.

### BUG-12. Свод остатков нескольких складов

Отчёт ждёт ответы всех складов. Один склад отвечает ошибкой.

Симптом: координация не завершается в отведённое время, хотя остальные ответы уже есть.

Инвариант: ожидание завершается и при ошибке участника; успешные остатки и список сбоев доступны вызывающему.

Тест: `Bug12Test`.

### BUG-13. Сводный оборот

Сводный отчёт запрашивает склады асинхронно и собирает сумму.

Симптом: вызов не возвращает сумму в отведённое время, прогресса нет.

Инвариант: метод возвращает сумму вкладов всех складов.

Тест: `Bug13Test`.

### BUG-14. Публикация правил цен

Фоновая задача сменяет политику скидок. Другие потоки читают уже опубликованную политику.

Симптом: читатель видит политику без правил, наценки или признака завершения заполнения.

Инвариант: любая политика, которую читатель уже наблюдает, полностью заполнена.

Тест: `Bug14Test`.

### BUG-15. Контекст организации в пуле

Фоновая обработка заказа хранит организацию в контексте потока. Следующая задача на том же потоке пула выполняет обслуживание без организации.

Симптом: обслуживание записывается как действие предыдущей организации.

Инвариант: после заказа организации A обслуживание не видит A; каждый заказ записывается со своей организацией.

Тест: `Bug15Test`.

## Четыре синхронизатора

Классы лежат в `ru.moysklad.concurrency.synchronizers`. Сейчас методы бросают `UnsupportedOperationException`. Конструкторы уже отвергают недопустимые аргументы.

Нельзя делегировать стандартным классам с тем же контрактом:

- `CustomCountDownLatch` — не `CountDownLatch`;
- `CustomSemaphore` — не `Semaphore`;
- `CustomReadWriteLock` — не `ReentrantReadWriteLock`;
- `CustomCyclicBarrier` — не `CyclicBarrier`.

Можно использовать `synchronized` / `wait` / `notifyAll`, `LockSupport`, `ReentrantLock` и `Condition` там, где это не подменяет сам заданный синхронизатор. Без активного ожидания (`busy waiting`).

### SYNC-01. `CustomCountDownLatch`

Сценарий: дождаться загрузки остатков со всех складов.

Операции: `await()`, `await(timeout, unit)`, `countDown()`, `getCount()`.

Контракт:

- несколько потоков ждут вместе и освобождаются, когда счётчик стал нулём;
- `countDown` не уводит счётчик ниже нуля;
- прерывание ожидания завершается `InterruptedException`;
- таймаут возвращает `false`, если ноль не достигнут, и не портит счётчик;
- ложное пробуждение не отпускает поток раньше нуля;
- при нулевом начальном счётчике `await` не блокируется.

Тест: `CustomCountDownLatchTest`.

### SYNC-02. `CustomSemaphore`

Сценарий: не больше N параллельных запросов к внешней системе.

Операции: `acquire()`, `tryAcquire()`, `tryAcquire(timeout, unit)`, `release()`, `availablePermits()`.

Контракт:

- одновременно внутри критической секции не больше выданных разрешений;
- `release` возвращает одно разрешение и будит ожидающего;
- разрешения не пропадают и не появляются сами;
- прерванное ожидание `acquire` не забирает разрешение;
- `tryAcquire` без таймаута не блокируется;
- таймаут возвращает `false`, если разрешение не получено.

Тест: `CustomSemaphoreTest`.

### SYNC-03. `CustomReadWriteLock`

Сценарий: много потоков читают каталог, один поток обновляет цены.

Операции: `lockRead()`, `unlockRead()`, `lockWrite()`, `unlockWrite()`.

Политика: предпочтение писателя. Пока писатель ждёт, новый читатель не входит. Так писатель не голодает при непрерывных читателях.

Контракт:

- несколько читателей одновременно;
- один писатель и ни одного читателя в это время;
- чтение и запись одновременно запрещены;
- `unlockRead` / `unlockWrite` с потока, который блокировку не держит, бросает `IllegalMonitorStateException`;
- прерывание ожидания завершается `InterruptedException`;
- повторный захват и повышение читателя до писателя не требуются и не поддерживаются контрактом.

Тест: `CustomReadWriteLockTest`.

### SYNC-04. `CustomCyclicBarrier`

Сценарий: потоки расчёта оборотов встречаются в конце этапа и идут на следующий этап тем же барьером.

Операции: `await()`, `await(timeout, unit)`, `reset()`, `getNumberWaiting()`.

Контракт:

- никто не проходит барьер, пока не пришли все `parties`;
- после прохода барьер сразу готов к следующему поколению;
- `await()` возвращает `parties - 1 - индексПрибытия`, последний участник возвращает 0;
- прерывание ломает поколение: прерванный поток получает `InterruptedException`, остальные этого поколения — `BrokenBarrierException`;
- таймаут ломает поколение: опоздавший получает `TimeoutException`, остальные — `BrokenBarrierException`;
- следующее `await` на сломанном барьере тоже получает `BrokenBarrierException`, пока не вызван `reset`;
- `reset` будит ожидающих с `BrokenBarrierException` и открывает новое исправное поколение;
- ложное пробуждение не отпускает поток раньше полного набора.

Тест: `CustomCyclicBarrierTest`.

## Критерии оценки

| Часть | Баллы |
|---|---|
| BUG-01 … BUG-15, по 4 балла | 60 |
| SYNC-01 … SYNC-04, по 8 баллов | 32 |
| Отчёт | 8 |
| Итого | 100 |

Баллы за ошибку ставятся, если соответствующий тест группы `bug` проходит, группа `baseline` не сломана и решение не маскирует дефект удалением зонда или подменой потока циклом.

Баллы за синхронизатор ставятся, если проходит его тестовый класс, нет делегирования запрещённому классу и нет активного ожидания.

## Отчёт

Отчёт на 6–10 страниц:

1. Для каждого BUG-XX: какой инвариант нарушался, какое состояние видели потоки, что изменено, почему это восстанавливает инвариант. Укажите альтернативу и её цену (блокировка, справедливость, отказ).
2. Для каждого синхронизатора: как устроены ожидание, пробуждение, прерывание и таймаут; где возникает отношение happens-before.
3. Какие тесты запускались и чем закончились `baseline`, `bug`, `synchronizer`.
4. Что сознательно не делалось: база данных, внешний API, замена потоков однопоточной имитацией.
